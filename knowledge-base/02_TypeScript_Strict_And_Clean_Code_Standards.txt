2. TYPE-SAFE ERROR HANDLING (RESULT<T, E> PATTERN)

Avoid throwing untyped errors across business logic. Use discriminated unions
for predictable error handling:

export type Result<T, E = Error> =
  | { success: true; data: T }
  | { success: false; error: E };

export async function safeFetchJson<T>(url: string): Promise<Result<T, string>> {
  try {
    const res = await fetch(url);
    if (!res.ok) {
      return { success: false, error: `HTTP Error: ${res.status}` };
    }
    const data = (await res.json()) as T;
    return { success: true, data };
  } catch (err) {
    return {
      success: false,
      error: err instanceof Error ? err.message : 'Unknown network error',
    };
  }
}



3. DISCRIMINATED UNIONS FOR UI & ASYNC STATES

NEVER use multiple boolean flags like isLoading, isError, isSuccess
simultaneously (which causes impossible states). Always use a single
discriminated union:

type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; data: T };

function renderUserState(state: AsyncState<{ name: string }>) {
  switch (state.status) {
    case 'idle':
      return 'Ready to load';
    case 'loading':
      return 'Loading user...';
    case 'error':
      return `Error: ${state.message}`;
    case 'success':
      return `Welcome, ${state.data.name}`;
  }
}



4. TYPE GUARDS & SATISFIES OPERATOR (ZERO AS CASTING)

 * NEVER use as SomeType to silence compiler errors. Write a proper runtime Type
   Guard (value is SomeType) or use the satisfies operator:

interface ApiError {
  code: number;
  message: string;
}

function isApiError(error: unknown): error is ApiError {
  return (
    typeof error === 'object' &&
    error !== null &&
    'code' in error &&
    typeof (error as Record<string, unknown>).code === 'number' &&
    'message' in error &&
    typeof (error as Record<string, unknown>).message === 'string'
  );
}

// Use `satisfies` to validate config objects without losing literal types
const ROUTES = {
  home: '/',

5. SYSTEMATIC DEBUGGING & LEGACY REFACTORING PROTOCOL

When asked to debug or refactor broken code, ALWAYS follow this 4-step sequence:
 1. Root Cause Isolation: Identify the exact line, race condition, state
    mutation, or type mismatch causing the bug before writing any fix.
 2. Guard Clauses (Early Returns): Flatten deeply nested if/else pyramids into
    clean early returns.
 3. Pure Function Extraction: Separate side effects (API calls, DOM updates, DB
    writes) from pure business calculations so logic is 100% testable.
 4. Regression Safety: Ensure existing public function signatures and API
    contracts remain unbroken unless explicitly asked to change them.

# TYPESCRIPT CODE CONVENTIONS & MODULAR ARCHITECTURE (FIXED & COMPLETE)

## 1. NAMING CONVENTIONS
- **Variables & Functions:** Use `camelCase` with descriptive verb-noun prefixes for functions (e.g., `fetchUserProfile`, `calculateOrderTotal`, `isValidEmail`).
- **Types, Interfaces & Classes:** Use `PascalCase` (e.g., `UserProfile`, `ApiResponse<T>`). Never prefix interfaces with `I` (use `User`, not `IUser`).
- **Constants & Env Keys:** Use `UPPER_SNAKE_CASE` for global immutable constants (e.g., `MAX_RETRY_ATTEMPTS = 3`).
- **Files & Directories:** Use `kebab-case.ts` / `kebab-case.tsx` for all files and folders (e.g., `auth-service.ts`, `user-card.tsx`).

## 2. STRICT TYPESCRIPT USAGE
- **Zero `any` Policy:** Never use `any`. Use `unknown` for unvalidated external data (API responses, JSON.parse) and narrow types using Zod schemas or custom Type Guards.
- **Explicit Return Types:** Always declare explicit return types on exported functions, server actions, and API handlers so accidental return mutations are caught at compile time.
- **Interface vs. Type:** Use `interface` for extendable object shapes and component props; use `type` for unions, intersections, mapped types, and function signatures.
- **Immutability by Default:** Use `readonly` properties on data models and `as const` assertions on configuration objects.

## 3. SYNTAX, FORMATTING & CLEAN EXAMPLE
- Prefer early returns (guard clauses) over deeply nested `if/else` blocks.
- Keep functions focused on a single responsibility (under 30 lines where practical).
- **Production Example (Type-Safe Service Function):**

interface UserRecord {
  readonly id: string;
  readonly email: string;
  readonly role: "admin" | "member";
}

export async function getAdminEmails(users: readonly UserRecord[]): Promise<string[]> {
  if (users.length === 0) {
    return [];
  }

  return users
    .filter((user): user is UserRecord & { role: "admin" } => user.role === "admin")
    .map((admin) => admin.email.toLowerCase());
}

## 4. FILE REFERENCE & LINK HYGIENE
- Always use real, verifiable project paths (e.g., `@/lib/utils`, `@/components/ui/button`) based on the actual project directory tree—never invent placeholder file paths or broken links.
